# 设计决策记录

每个决策回答"为什么这么做、备选是什么"。面试或 PR review 被追问时，答案在这里。

## D1 遥测通道按 schema 内容识别，不写死通道名

**决策**：扫描全部 jsonschema 通道，schema 文本含 `capture_to_submit_ms` 即认定为遥测通道。

**为什么**：工具的定位是"任何队的同形录像都能用"。通道名（`/ace/debug/auto_aim`）、
schema 名（`ace.DebugFrame.v1`）都是队内约定，改名是常态；但
`capture_to_submit_ms` 是本工具依赖的最小语义契约，按它识别最稳。

**备选**：配置文件映射通道名（v1 弃用：多一步配置就少一次开箱即用；v0.2 引入
映射文件作为跨队 fallback，见 D7）。

## D7 跨队适配 = 指纹 + 字段路径两层映射，默认全内置

**决策**：`mapping.py` 维护"规范字段名 -> 消息内点分路径"的映射表，默认值即
ACE 格式；YAML 文件可覆盖指纹字符串与任意字段路径，未覆盖的键回落默认。

**为什么两层**：别的队与 ACE 的差异发生在两处——schema 里"必然出现的字符串"
（识别用）和字段命名（提取用）。通道名不是差异点（自动发现），字段名才是
（`t_cam` vs `capture_ns`）。只映射字段不映射指纹会识别失败，反之提取失败。

**为什么校验规范名白名单**：规范名被 analysis/report 硬引用（`stamp_ns`、
`written` 等列名），映射到不存在的规范名只会在下游深处报 KeyError；启动期
白名单校验把错误提前到配置加载时，且报错信息能列出合法名字。

**为什么 YAML**：配置文件的读者是"想接入自己队伍的陌生学生"，YAML 支持注释、
缩进即结构；JSON 不支持注释，会逼人去 README 查每个键的含义。

**备选**：JSON Schema 自动推断（过度设计——字段语义工具无法推断，比如哪个
时间戳是曝光时刻，只有队里的人知道）。

## D8 debugger 计数字段从默认映射中移除

**决策**：v0.2 默认映射只保留 header/timing/serial_tx 字段，debugger 计数不再提取。

**为什么**：v0.1 提取了但 analysis/report 没有任何一处消费——死列。摄取层的
列集合应该由"下游用了什么"定义，而不是"源数据有什么"；后者是 v0.1 的惯性。
需要时加回来是一行配置的事（这正是映射层存在的意义）。

## D9 交互界面 = 本地 Web 应用，而非桌面 GUI 或 Streamlit

**决策**：`rm-latency serve` 起本地 FastAPI 服务（仅绑 127.0.0.1），浏览器做前端。

**为什么不是桌面 GUI（Qt）**：分析逻辑在 Python 里，Qt 界面意味着全部交互代码
与已验证的分析代码平行存在一份绑定层；且目标用户环境（无 sudo 的 Ubuntu 训练机、
各队参差的桌面环境）下 Qt 依赖与打包是持续税。浏览器是 TensorBoard/Jupyter
验证过的分析工具形态。

**为什么不是 Streamlit/Gradio**：能跑，但"分位数随缩放视野实时重算"这类交互在
其重跑模型下天然别扭；且用低代码框架做工具，工程含量在简历上是要打折的——
这个项目的定位包含作品集价值。

**为什么下发全量时序数组而不是前端再请求**：分位数在前端对任意缩放区间重算，
逐帧数组是重算的原料；50k 点上限抽稀（统计仍用全量）保证浏览器不卡。

**安全边界**：单机工具，默认回环地址；上传的录像写入临时文件、分析完即删。

## D10 视频回放 = 逐帧 JPEG 接口 + 内存会话缓存，而非 MP4 转码

**决策**：分析时把 CompressedImage 通道解包进服务端会话缓存（帧字节 + 对齐时间戳），
前端经 `/api/frame/{run}/{i}` 逐帧取图；超上限按等步长抽稀覆盖全时段。

**为什么不做 MP4**：转码引入 ffmpeg 依赖与关键帧 seek 精度损失；而本工具的
视频不是"看录像"，是**与延迟时序帧级对齐的证据**——点时序图 t=32.5s 就要看
那一瞬间的输入画面，逐帧接口天然精确，且 JPEG 本来就是 MCAP 里存的形态，
零转码零再压缩。

**为什么内存缓存而不是临时文件**：帧在会话内被反复随机访问（拖动滑条），
内存读是零延迟；LRU 保留最近 3 份录像、单录像帧数上限抽稀，内存有界。
进程退出即释放，不落盘是刻意的——工具不留用户数据的副本。

**为什么抽稀而不是截断**：初版按帧数从头截断，真实录像冒烟暴露视频只覆盖
前 87% 时间轴——时间轴尾部点不出画面会误导复盘。改为跨全时段等步长抽稀
（1/stride），精度损失均匀分布，完整性优先。

**时钟域对齐**：图像 log_time 是墙钟域、遥测 stamp_ns 是单调域，偏移取
遥测 median(log_time - stamp)。用中位数而不是首帧差：首帧两端可能非同时记录，
稳态偏移才是真偏移。

## D2 纳秒字段按字符串读取后转 int64

**决策**：`capture_ns` 等字段在遥测 JSON 里是字符串，读取时 `int()` 转换。

**为什么**：单调时钟的纳秒值远超 IEEE double 的安全整数范围（2^53），JSON
number 会丢精度；上游写字符串是正确做法，工具端必须按 int64 处理，任何时刻
不允许把 ns 值装进 float。

**后果**：pandas 列 dtype 必须是 int64/float64（NaN 容错）而不是 object，
`test_load_frames_shape_and_order` 里有 dtype 断言守住这一点。

## D3 累计计数器在摄取层原样保留，差分在分析层做

**决策**：`serial_tx` / `debugger` 的计数是累计值，ingest 不加工。

**为什么**：差分会丢失"计数器回退"信息（设备重启），且差分方式（邻帧 diff vs
窗口 diff）是分析层的表达选择。分层后分析代码换差分策略不用重读文件。

**后果**：`serial_tx_deltas` 对负 diff（回退）clip 到 0 并留 `counter_resets`
标记列。

## D4 plotly.js 整包内联进报告 HTML

**决策**：单文件 HTML，plotly.js（约 3MB）内联，离线可打开。

**为什么**：目标用户是赛场边/训练场的队员，不能假设有外网；CDN 版本漂移也会
让历史报告无法复现当时的渲染。

**备选**：CDN 引用（体积小但离线不可用）、静态 matplotlib PNG（失去悬停交互）。

## D5 掉帧判据：间隔 > 1.5×中位数 且 > 1 ms

**决策**：`GAP_FACTOR = 1.5`，双条件。

**为什么不用 2.0**：恰好丢一帧产生**精确 2× 中位数**的间隔，"严格大于 2×"
的判据永远抓不到最常见、最重要的单帧掉落——这是初版测试直接暴露的缺陷。
**为什么敢用 1.5**：相机稳态周期下抖动通常远小于周期的 25%，1.5 倍不会误报；
1 ms 绝对下限兜底低帧率场景。中位数而非均值做基准，抗毛刺。

## D6 时序图超过 5000 点抽稀，抽稀比例写进图上

**决策**：等步长抽稀，标注 `1/N`。

**为什么**：一场 10 分钟 240fps 的录像约 14 万帧，全量画线浏览器渲染卡死；
等步长抽稀保形最好（峰谷仍可见，随机抽样反而会糊掉周期性尖峰）。标注比例是
诚实原则：读者有权知道看到的是抽样不是全量。
