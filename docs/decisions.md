# 设计决策记录

每个决策回答"为什么这么做、备选是什么"。面试或 PR review 被追问时，答案在这里。

## D1 遥测通道按 schema 内容识别，不写死通道名

**决策**：扫描全部 jsonschema 通道，schema 文本含 `capture_to_submit_ms` 即认定为遥测通道。

**为什么**：工具的定位是"任何队的同形录像都能用"。通道名（`/ace/debug/auto_aim`）、
schema 名（`ace.DebugFrame.v1`）都是队内约定，改名是常态；但
`capture_to_submit_ms` 是本工具依赖的最小语义契约，按它识别最稳。

**备选**：配置文件映射通道名（v1 弃用：多一步配置就少一次开箱即用；Phase 4
做跨队适配时再引入 YAML 映射作为 fallback）。

## D2 纳秒字段按字符串读取后转 int64

**决策**：`capture_ns` 等字段在遥测 JSON 里是字符串，读取时 `int()` 转换。

**为什么**：单调时钟的纳秒值远超 IEEE double 的安全整数范围（2^53），JSON
number 会丢精度；上游写字符串是正确做法，工具端必须按 int64 处理，任何时刻
不允许把 ns 值装进 float。

**后果**：pandas 列 dtype 必须是 int64/float64（NaN 容错）而不是 object，
`test_load_frames_shape_and_order` 里有 dtype 断言守住这一点。

## D3 累计计数器在摄取层原样保留，差分在分析层做

**决策**：`serial_tx` / `debugger` 的计数是累计值，ingest 不加工。

**为什么**：差分会丢失"计数器回退"信息（设备重启），且差分方式（邻帧 diff vs
窗口 diff）是分析层的表达选择。分层后分析代码换差分策略不用重读文件。

**后果**：`serial_tx_deltas` 对负 diff（回退）clip 到 0 并留 `counter_resets`
标记列。

## D4 plotly.js 整包内联进报告 HTML

**决策**：单文件 HTML，plotly.js（约 3MB）内联，离线可打开。

**为什么**：目标用户是赛场边/训练场的队员，不能假设有外网；CDN 版本漂移也会
让历史报告无法复现当时的渲染。

**备选**：CDN 引用（体积小但离线不可用）、静态 matplotlib PNG（失去悬停交互）。

## D5 掉帧判据：间隔 > 1.5×中位数 且 > 1 ms

**决策**：`GAP_FACTOR = 1.5`，双条件。

**为什么不用 2.0**：恰好丢一帧产生**精确 2× 中位数**的间隔，"严格大于 2×"
的判据永远抓不到最常见、最重要的单帧掉落——这是初版测试直接暴露的缺陷。
**为什么敢用 1.5**：相机稳态周期下抖动通常远小于周期的 25%，1.5 倍不会误报；
1 ms 绝对下限兜底低帧率场景。中位数而非均值做基准，抗毛刺。

## D6 时序图超过 5000 点抽稀，抽稀比例写进图上

**决策**：等步长抽稀，标注 `1/N`。

**为什么**：一场 10 分钟 240fps 的录像约 14 万帧，全量画线浏览器渲染卡死；
等步长抽稀保形最好（峰谷仍可见，随机抽样反而会糊掉周期性尖峰）。标注比例是
诚实原则：读者有权知道看到的是抽样不是全量。
